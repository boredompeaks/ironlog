# rework.md — IronLog architecture & editing map

Written for a future AI agent (or future you) picking this codebase back up with zero
prior context. Read this before touching `index.html`.

## 1. What this app is, and why it's built this way

**Goal:** a fully offline, single-file personal strength & conditioning trainer for a
beginner-to-intermediate lifter. It replaces a paper log + guesswork with three small
"expert system" engines (progression, recovery, volume) that encode real trainer logic as
plain if/else decision trees — not machine learning, not an API call. The user explicitly
wants to export raw + summarized data weekly as a `.txt` file and paste it into a separate
AI conversation for deeper bespoke coaching, so this app deliberately does NOT call any AI
API itself. Keep it that way unless the product direction changes.

**Architecture:** Originally a single-file "godfile", this has been explicitly modularized into a standard SPA structure inside the `www/` directory (`www/index.html` + `www/js/*.js`). This keeps the app fully offline and Capacitor-ready without a bundler, while separating concerns (state, engines, ui, screens).

**Why JSON + localStorage, not a database:** single user, small data volume (years of gym
logs is still only a few MB), and the user wants the raw data human-readable/exportable.
See `defaultState()` for the full schema. `saveState()`/`loadState()` are the only two
functions that touch `localStorage` — if you ever add a native file-backed store (e.g. via
the Capacitor Filesystem plugin), those two functions are the only things you need to swap.

**Scope boundary — deferred to v3, do not build yet unless asked:**
- "Advanced" training-age tier (periodization, MEV/MAV/MRV numeric bands exposed to the
  user, autoregulated programming). Currently `trainingAge` only has `beginner` and
  `intermediate`. The Progression/Recovery engines are written generically enough that
  adding an `advanced` branch later should mostly mean adding new `if` branches inside
  `getProgressionSuggestion()` and `getMuscleRecoveryStatus()`, not a rewrite.
- Any Gemini/AI API integration. If this gets added later, it should be strictly additive
  (an "Ask Coach" feature reading from `AppState`), never a replacement for the offline
  rule engines.
- Wearable/HR integration — cardio logging is manual-entry only by design (see Section 6
  of the exercise catalog / cardio logging in `openLogModal`).

## 3. `www/js/` internal structure

The logic is split across the following files in `www/js/`:

| File | Purpose |
|---|---|
| `constants.js` | `MUSCLE_GROUPS`, `CATALOG` array, `SPLIT_PRESETS`, `SCHEMA_VERSION` |
| `state.js` | `defaultState()`, `loadState()`, `saveState()`, schema migration — the data schema |
| `engines.js` | Metabolic math, Progression engine (`getProgressionSuggestion()`), Recovery engine |
| `report.js` | `generateWeeklyReport()`, `exportWeeklyReport()`, Capacitor clipboard hooks |
| `ui.js` | `route`, `render()`, `renderModals()`, focus preservation, manual rest timer |
| `screens.js` | `renderOnboarding()`, `renderToday()`, `renderTemplates()`, logging forms |
| `boot.js` | `window.onload` — calls `maybeAutoExport()` then first `render()` |

Every function has a JSDoc docstring explaining purpose, params, and
return shape — read those before modifying a function's behavior, especially the three
engines (Sections 3-7), since their thresholds encode actual trainer logic decisions that
were deliberately chosen (see Section 5 below for the specific numbers and rationale).

## 4. How the render loop works (important before editing any UI)

There is no virtual DOM. `render()` (Section 9) fully re-generates the relevant screen's
`innerHTML` from `AppState` + any relevant draft variable (`onboardDraft`, `logDraft`,
`templateDraft`) every time it's called. The pattern for every mutation is:

```js
function someAction(){
  AppState.something = newValue;   // 1. mutate state (or a *Draft variable for in-progress forms)
  saveState();                     // 2. persist (skip this for *Draft-only changes pre-save)
  render();                        // 3. re-render whatever screen is active
}
```

If you add a new screen: add a route id, add a branch in the `render()` dispatcher, add a
tab in `renderTabbar()` if it should be user-facing, write a `renderYourScreen()` function
following the existing naming convention.

If you add a new modal: push an id onto `modalStack`, add a branch in `renderModals()`,
write `renderYourModal()`, and give it a `closeModal()`-compatible cancel path.

## 5. Where the actual "trainer logic" numbers live (edit with care)

These are the specific thresholds a real trainer's judgment was translated into code.
Changing them changes the app's coaching behavior, not just its UI:

- **Progression engine** (`getProgressionSuggestion`, Section 4): increase weight after 2
  consecutive sessions at top of rep range; deload 10% after 2 consecutive sessions missing
  bottom of rep range. Increment size comes from `getIncrement()`, which prefers a
  per-machine user calibration (`AppState.machineCalibration`) over `CATALOG[].defaultIncrement`.
- **Recovery engine** (`getMuscleRecoveryStatus`, Section 5): soreness >=4/5 with <2 days
  rest -> rest. Soreness >=3 OR flat/declining e1RM trend with <3 days rest -> caution.
  Otherwise -> train. Whole-body deload (`shouldSuggestFullDeload`) triggers at 3+
  simultaneously rest-flagged muscle groups.
- **Volume bands** (`VOLUME_BANDS`, Section 6): 8-20 sets/week/muscle group is the
  "good" band, deliberately coarse (low/good/high) rather than exposing raw MEV/MAV/MRV
  numbers per the beginner-friendly design goal. If/when the deferred "advanced" tier is
  built, this is likely where you'd branch to a more granular numeric display.
- **Outlier guard** (`isOutlierWeight`, Section 12): flags a logged weight >2x or <0.4x the
  historical average for that exercise, requires a second Save tap to confirm. This exists
  specifically to catch fat-finger typos before they corrupt PB tracking — don't remove
  without a replacement safeguard.

## 6. Data schema quick reference (`defaultState()`, Section 2)

```
AppState.profile              -> UserProfile (null until onboarding completes)
AppState.machineCalibration   -> { [catalogId]: { increment, plateWeight, barWeight } }
AppState.customExercises      -> CatalogItem[] (user-added, merged into fullCatalog())
AppState.templates            -> { id, name, exerciseIds: [] }[]
AppState.activeSplit          -> { templateIds: [] } — which templates rotate in "Today"
AppState.sessions             -> { id, dateISO, exerciseId, sets?|cardio?, soreness?, templateId? }[]
AppState.bodyweightLog        -> { dateISO, kg }[]
AppState.injuryFlags          -> { [catalogId]: { until, note } }
AppState.lastWeeklyExport     -> ISO date string
AppState.lastSessionByExercise -> { [catalogId]: dateISO } (lookup cache)
```

`fullCatalog()` = `CATALOG` (Section 1, static presets) + `AppState.customExercises`.
Always read exercises through `getCatalogItem(id)` / `fullCatalog()`, never `CATALOG`
directly, or custom exercises will silently break in every screen.

## 7. Common edit scenarios

- **Add a new preset machine:** add one object to the `CATALOG` array (Section 1). Follow
  the existing shape exactly, including a 3-line-max `info` string.
- **Change progression math:** edit `getProgressionSuggestion()` (Section 4) only. Don't
  duplicate this logic elsewhere — every screen calls this same function.
- **Change what counts as "rested":** edit `getMuscleRecoveryStatus()` (Section 5) only.
- **Change the weekly report format:** edit `generateWeeklyReport()` (Section 8) — it's a
  single string-builder function, safe to restructure freely since nothing else parses its
  output (it's meant for a human/another AI to read, not for this app to re-ingest).
- **Add the advanced tier (v3):** add `'advanced'` as a `trainingAge` option in
  `renderOnboarding()` (Section 10), then branch on it inside the three engines (Sections
  4/5/6) and in `renderDashboard()` if advanced users should see raw MEV/MAV/MRV numbers
  instead of low/good/high.
